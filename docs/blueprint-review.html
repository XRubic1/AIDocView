Blueprint System Review

What works, what is broken, and how to make chase automation easy to set up and easy to watch, without throwing away the graph engine you already built.

Short version

The idea is right and the vocabulary (Start → Wait → When → Then do → Done) is good. The problem is that the system runs in two places with two copies of the logic, and the server copy does not actually read what users draw. So users wire up a canvas, and the server picks a blueprint by guessing from which cards exist. That gap is the root of most of the "confusing" feeling. Fix the plumbing first (one engine, on the server, driven by database events), then make building easier with a sentence-style recipe builder that saves the same graph JSON, and add a Task board on top of the runs table.

What is good

  • A clear card vocabularyStart with / Wait until / When / Then do / Done maps well to how A/R staff think about follow-up.
  • Shared recipe, per-invoice pointerInvoices store which blueprint and step they are on, not a copy of the graph. Correct model.
  • Domain-aware wait clocksnet_plus_late, due_plus_late, after_last_email, no_payments_for are real A/R timing, not generic timers.
  • Connection rulesblueprintConnectionRules.ts blocks links that the runner can't execute and blocks broker cards on invoice graphs.
  • Dry run and run historySimulating a path and storing history jsonb per run gives you the raw material for a timeline view.
  • Standard blueprints are seededPaperwork chase, payment chase, hold notice, packet, dispute, broker replies. These are effectively your templates already.
  • Server cron existsblueprint-wake-cron runs chase with no tab open. Good direction, it just needs to become the only engine.
  • Tested24 files / 110 tests pass for blueprints and services. Not one tests that browser and server engines agree, though.

How it runs today

What is broken, ranked

  1. The Live runner switch does not stop the server. Docs say the wake cron no-ops when Live is off, but runBlueprintServerTick never reads blueprints_runtime. email-lifecycle-chase also calls the same tick. If the cron is scheduled, chase emails go out with the switch off.
    supabase/functions/_shared/blueprintEngine.ts:628 · supabase/functions/email-lifecycle-chase/index.ts:43
  2. The server ignores what you draw on Start. pickBlueprint filters by status (hold / approved / review) then picks by trackOf(), which guesses a track from which When/Then-do cards exist. A custom blueprint that doesn't fit a known track is classed "other" and never auto-enrolls on the server. This is the biggest reason the editor feels like it doesn't do what it says.
    blueprintEngine.ts:167 trackOf · :505 pickBlueprint
  3. Two engines disagree. Example: invoice_processed is true for approved/hold/paid/force_closed in the browser, and approved/hold/review on the server. An unknown When check defaults to true in the browser and false on the server. Same invoice, different path depending on who ticked it. Invoice, broker and batch runners in the browser also each carry their own copy of nextNodes/pickNext.
    src/components/blueprints/blueprintRunner.ts:97 vs blueprintEngine.ts:291
  4. Events only exist inside an admin's browser tab. emitCredyxEvent is a window event bus. Changes from the client portal, email-inbound or batch AI don't fire hold/PPW/paid hooks; they wait for the cron. The cron only loads approved/review/hold invoices, .limit(200) with no ordering, and 400 live runs. Pending invoices are never scanned, and past 200 open invoices some are silently skipped each tick.
    src/services/credyxEvents.ts · blueprintEngine.ts:657–680
  5. Demo runs can show up as real data. ensureBlueprintRunsSeeded writes fake runs (INV-10482, INV-10501…) whenever the local list is empty, including right after a hydrate that returned zero rows. findRunsForInvoice then matches runs without a subject id to invoices by invoice-number label, so a real invoice with that number would show a fake run.
    src/components/blueprints/blueprintRuns.ts:221 · :278
  6. Nothing guarantees one active run per invoice. The docs rule is "one active chase run per invoice", but blueprint_runs has no partial unique index. The browser lock (withInvoiceEnrollLock) is in-memory per tab, so two admins, or an admin plus the cron, can double-enroll and double-email.
    supabase/migrations/20260924180000_blueprints.sql · blueprintRunner.ts:1550
  7. localStorage is treated as a source of truth. Graphs, runs and the handoff map live in localStorage and write through to Supabase without awaiting. Two admins editing get last-write-wins on the whole graph. Graphs aren't versioned, so editing a blueprint while invoices sit on a step can leave current_node_id pointing at a card that no longer exists. Every admin login also runs syncAllOpenInvoiceBlueprints across all open invoices from the browser.
    blueprintStore.ts · blueprintRuns.ts · src/services/supabase/hydrateStores.ts:66
  8. Reply-based Whens never fire. broker_replied and no_reply are hard-coded false in both engines, and the server drops any blueprint that uses them. They still appear in the editor, so users can build a blueprint that parks forever.
    blueprintRunner.ts:126 · blueprintEngine.ts:157, 302

How it should run

Setting up a new task

Most chase recipes are a straight line. A sentence builder covers them in four picks and saves the exact same nodes/edges, so the engine and the canvas still work. Branches (When yes/no) stay available in the Advanced view.

Task window

One screen for all work, built from blueprint_runs and a new blueprint_tasks table. Waiting runs are "Pending", staff tasks are "To do", paused or failed runs are "Needs attention".
